# On-chain reconciliation tool

Fetches real Sepolia events via RPC, computes what the `ens-v-2-test` subgraph *should* contain for each one by porting the actual mapping logic (not guessing), queries the live deployment, and diffs field-by-field. Self-contained (`npm install` in this directory only — doesn't touch the subgraph's own `package.json`/`yarn.lock`).

See the reconciliation plan this was built from (`/home/ciaran/.claude/plans/effervescent-noodling-anchor.md` at the time of writing) and the write-up in the `ens-subgraph-workspace` repo's `docs/reconciliation-report.md` for the actual findings from running this.

## Running it

```bash
npm install
node run.mjs          # appends to report.jsonl
node run.mjs --fresh   # clears report.jsonl first
node summarize.mjs     # reads report.jsonl, writes report.json, prints a console summary
```

`run.mjs` no longer resets `report.jsonl` by default (`--fresh` opts in) — an earlier run in this session lost a substantial, real partial result (1749 checks) to an unconditional reset on relaunch after a crash. Since `summarize.mjs` doesn't dedupe, re-running without `--fresh` after a successful full run will double-count matches; use `--fresh` for a genuine from-scratch run and only omit it when deliberately resuming/topping up after an interrupted one.

## Scope

- **ENSv2 (all sources): full coverage.** Every event type wired in `subgraph.yaml`, every occurrence, `startBlock`→head, for `RootRegistry`, `ETHRegistry`, every dynamically-discovered `UserRegistry`, `ETHRegistrar`, `VerifiableFactory`, and every discovered `PermissionedResolver` instance. Tractable because real ENSv2 event volume on this deployment is small (dozens to low hundreds per source).
- **ENSv1 (all 6 addressed contracts + NameWrapper + discovered `Resolver` instances): bounded sample, not full history.** Real event volume turned out to be in the hundreds of thousands per contract (ENSRegistry: 209,716 raw logs; BaseRegistrar: 149,327 — confirmed live, not estimated) across ENSRegistry's full ~7.86M-block history, making full per-event GraphQL cross-checking impractical. Sample per contract: the most recent 5,000 blocks plus 5 randomly-chosen 5,000-block windows spread across the full history, each window's events fully decoded and reconciled (not sub-sampled further). Resolver instances: a random sample of 15 out of 614+ discovered addresses, each checked over its own recent+random windows. Every event type still gets real exact-match checks — just not every historical occurrence of it.
- **Edge cases**: specific interesting real rows found by querying the subgraph itself (locked/high-fuse wrapped names, renewed registrations, unwrap events, multi-transfer chains), each independently re-verified via a single-block `eth_getLogs` call scoped to that row's own `blockNumber` — not `eth_getTransactionReceipt` (see below).

## Known scope limits (read before trusting a "mismatch")

- **`Domain.name`/`labelName` (and the equivalent on other ENSv1 entities) are not independently checked.** `src/ensRegistry.ts` derives these via graph-node's built-in `ens.nameByHash()` reverse-hash lookup, which this tool has no access to and cannot reproduce. `owner`/`parent`/`labelhash`/`ttl`/`resolver` are checked; the human-readable name fields aren't.
- **Bounded-window "current state" checks can false-positive.** A check like `checkDomainsCurrentState` (or any `*-latest`/`*-current-state` function) computes an expected value from whatever events happen to fall inside one sampled window, then compares it against the *live* entity — which reflects the true latest state across all history, not just this window. If a later event outside the sampled window changed the same field, the check reports a spurious `mismatch` even though the subgraph is correct. Confirmed live: a `Domain.resolver` "mismatch" found this way turned out to be exactly this — a real, more recent `NewResolver` event outside the window had updated it. **Any `mismatch` from a current-state check needs the actual on-chain history checked before being treated as a real defect; `mismatch`/`not_found` results from immutable history-entity checks (event-scoped, no ordering dependency) don't have this problem and can be trusted directly.**
- **ENSRegistryOld's `isMigrated`-conditional handlers are out of scope entirely**, not just under-sampled — `src/ensRegistry.ts`'s old-registry handlers gate on cross-registry migration state that would need a full ordered replay across both registries together to resolve correctly. Pre-2017 legacy code this session never touched; explicit scope decision, not an oversight.
- **`WrappedDomain`'s placeholder-then-reconcile race and `TokenRegenerated` chains** (where a `TransferSingle`/`TokenResource` can arrive in either order relative to the event that "really" establishes state) aren't independently replayed — the current-state checks for these read whatever the live entity says post-placeholder-reconciliation, not a from-scratch simulation of the race itself.

## Infrastructure findings from building this (useful if you have to touch RPC/GraphQL config again)

- **`https://ethereum-sepolia-rpc.publicnode.com` silently returns wrong data.** Confirmed live: `eth_getLogs` returned an empty result set for a block the subgraph itself reported a real event in (144 real transactions in that block, network-wide `eth_getLogs` with no filter also returned zero), and `eth_getTransactionReceipt` returned `null` for a transaction hash confirmed present via `eth_getBlockByNumber`. Not a rate limit or an error — a wrong, silent answer. Do not use this provider for anything this tool does.
- **`https://gateway.tenderly.co/public/sepolia` (`RPC_URL` in `config.mjs`) is correct for explicit bounded ranges, but silently wrong for `toBlock: "latest"`.** Confirmed live: the identical address queried with `fromBlock`/`toBlock` as explicit numbers vs. with `toBlock: "latest"` gave contradictory results (4 vs. 209,716+ logs) for a range that should be a strict subset. **Never pass the literal string `"latest"` to this provider** — every call site in this tool resolves it via `getBlockNumber()` to an explicit number first; keep that convention if you add new call sites.
- **Tenderly's gateway caps `eth_getLogs` at ~20,000 results per call**, not a fixed block-range size — block density on this chain isn't uniform, so a fixed-size chunk can still trip the cap. `lib/rpc.mjs::getLogsRange` handles this by recursively halving the range on that specific error rather than assuming any one chunk size is always safe.
- **The Studio GraphQL endpoint (`SUBGRAPH_URL`) rate-limits under this tool's sustained query volume**, returning a plain-text `"Too many requests, please try again later."` body (not JSON) once triggered. Once tripped in this session (by a ~2,000-request run), it did not clear within ~9 minutes of waiting across several cooldown attempts — a sustained block, not a short burst window. `lib/subgraph.mjs::query` paces every call (`MIN_INTERVAL_MS`) to avoid tripping it in the first place, plus retries with backoff as a fallback; widen `MIN_INTERVAL_MS` further if a future run trips it again, and budget real wall-clock time for a full sweep as a result.
